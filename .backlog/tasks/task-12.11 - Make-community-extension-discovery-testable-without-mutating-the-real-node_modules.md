## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Two tests in `check-node/src/config/load-config.spec.ts` install mock packages into the package's **real** `node_modules` (via `thisNodeModuleRoot()`), because sibling discovery for globally-installed extensions is defined relative to the installed location and a temp dir cannot stand in for it.

This caused a genuine intermittent CI failure, diagnosed rather than guessed: with spec files running in parallel, one worker created `platformos-check-global-extension` and deleted it while another worker's `loadConfig` was scanning the same directory, producing `Error loading …/node_modules/platformos-check-global-extension, ignoring it. Cannot find module …`. It surfaced in 1 of 8 runs as a log line and at least once as a hard test failure. Also found `not-conventional` left behind in the repo's `node_modules` from an earlier interrupted run — invisible to `git status` because the directory is gitignored.

Two mitigations already landed and are on this branch:
- unconditional cleanup of both mock packages in `beforeEach`/`afterEach`, so a throwing test cannot leave litter;
- the vitest pool keys moved to `poolOptions` (they were at `test.forks` and therefore ignored), restoring the intended single-fork serialization — after which 0 of 8 runs logged the error.

Those make it reliable but leave the root cause: tests write into a directory shared with the running process, and correctness now depends on serialization. That costs CI time (check-common 66 → 84 s, LSP 59 → 74 s, check-node 13 → 20 s, ~20% overall) and silently forbids re-enabling parallelism later.

The real fix is to make the installation root injectable so discovery can be pointed at a temp directory: `installation-location.ts` currently resolves it from `__dirname` with only a `WEBPACK_MODE` branch. Threading an override through the config loader (or an explicit seam like the graph cache's test seams) would let both tests be hermetic, and would let the fork limit be relaxed again.
