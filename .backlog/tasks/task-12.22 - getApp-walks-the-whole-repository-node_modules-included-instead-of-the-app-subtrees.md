## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Measured while profiling TASK-12.6 (2026-07-31).

`getAppFilesPathPattern` is `<root>/**/*.{liquid,graphql,yml,yaml}` with no ignore, so
the glob walks every `node_modules` tree in the project. Both real projects profiled
have plenty:

| Project | node_modules dirs | liquid/yml/graphql files inside them | of those, kept in the App |
|---|---|---|---|
| pos-module-community | 7 | 25 | **0** |
| arabbank | 43 | 172 | **0** |

So the classification filter is doing its job — not one node_modules file survives into
the `App`. The cost is purely the WALK, and it is now the dominant remaining cost of a
warm `validate_code` call:

| | community (944 files) | arabbank (3140 files) |
|---|---|---|
| `getApp` (glob + classify) | 187 ms | 262 ms |
| warm `lintBuffer` TOTAL | 159 ms | 257 ms |

`getApp` does 0 reads, 0 stats and 0 parses, so essentially all of it is the directory
walk — and most of the walk is directories that cannot contain an app file.

## Fix

Pass an ignore to `glob` (`node_modules/**`, `.git/**`, `dist/**`, `tmp/**`, `vendor/**`
— `check-common/src/context-utils.ts` already has that exact list as `ignoredFolders`
for `recursiveReadDirectory`, so it should be shared rather than re-listed). Then
measure again: the walk should drop to the app/modules subtrees only.

Note this composes with, and is cheaper than, TASK-12.19 (reuse one App per process
instead of re-globbing): a cheap glob may make the reuse unnecessary.

## Done — the fix is anchoring, and check-node stopped classifying

### The ignore list in this task's Fix section was the wrong idea, twice over

It proposed sharing `context-utils.ts`'s `ignoredFolders`
(`.git`, `node_modules`, `dist`, `build`, `tmp`, `vendor`) with the glob. A
directory-name blacklist is wrong in both directions:

- **It drops real app files.** Measured over ~200 projects in `~/projects/pos`, taking
  every `.liquid`/`.graphql`/`.yml`/`.yaml` under a directory with one of those names
  and asking the classifier whether it is an app source: `vendor` 133/133 are real
  (`htevent/app/views/pages/vendor/**`, a whole section of a live site), `tmp` 123/126,
  `build` 6/6 (`Accala-MP/app/lib/commands/v2/projects/update/build/*.liquid`).
  `node_modules` 0/3674 and `.git` 0/0 — but that is luck, not a rule.
- **It keeps walking places no app file can be.** `tmp/app/views/partials/x.liquid` is
  not a partial. Not because it is under `tmp`, but because from the ROOT it is not
  under `app/`, `marketplace_builder/` or `modules/<name>/(public|private)/`.

That anchoring rule is `parseAppPath`'s grammar and has always been the classifier's
answer. `APP_SOURCE_SUBTREES` in `platformos-common` now states it as a PREFIX so a walk
can use it — `['app', 'marketplace_builder', 'modules/*/public', 'modules/*/private']`,
derived from `APP_ROOTS`/`MODULE_ROOTS`/`ACCESS_LEVELS` (`app/modules/<name>/…` needs no
entry: it is under `app`). `app-source-subtrees.spec.ts` pins coverage in both
directions — every path `parseAppPath` accepts is inside a subtree, and the six shapes
above are outside every subtree AND rejected by `parseAppPath`.

`check-node` globs one pattern per subtree. Nothing is blacklisted; `node_modules` is
simply never reached, including `modules/core/react-app/node_modules/**` (433 candidate
files in Accala-MP), which no root-level prune would have caught.

### check-node stopped classifying entirely

Raised in review: the `isKnownLiquidFile`/`isKnownGraphQLFile`/`isKnownYAMLFile` filter in
`getAppFilePaths` was a second opinion about what a platformOS file is, in a package that
should hold none — the same knowledge leak `directory-knowledge.spec.ts` already polices
for directory names. It is gone. `getAppFilePaths` yields CANDIDATES (source extension,
minus the user's configured `ignore`) and `App.fromPaths`/`parseAppPath` decides. Both the
subtrees and `SOURCE_FILE_EXTENSIONS` (derived from `REFERENCE_EXTENSIONS`) come from
`platformos-common`, so adding a file type reaches the walk for free.

The filter turned out to be pure duplication — identical app, file by file, on all four
projects below. Three remaining copies of this knowledge outside `platformos-common`
(the LSP's file-operation glob, `to-source-code.ts`, the graph's walk filter): TASK-12.27.
`recursiveReadDirectory` makes the blacklist mistake for the graph build and the LSP
preload: TASK-12.25, reframed around anchoring.

### AC #2 — measured

Three variants alternating in ONE process, 5 iterations, median. `original` = whole-tree
glob + isKnown* filter; `blacklist` = whole-tree glob pruned by `node_modules`/`.git`;
`anchored` = shipped.

Whole `getApp`:

| project | app files | identical to original | original | blacklist | anchored |
|---|---|---|---|---|---|
| pos-module-community | 946 | yes | 224 ms | 215 ms | 201 ms |
| arabbank | 3139 | yes | 381 ms | 146 ms | 154 ms |
| Accala-MP | 2789 | yes | 1289 ms | 203 ms | **152 ms** |
| htevent (no node_modules) | 2895 | yes | 126 ms | 116 ms | 128 ms |

The walk alone, which is what this task is about (the totals above are dominated by
`isIgnored` — see TASK-12.26):

| project | whole-tree | blacklist | anchored | candidates yielded |
|---|---|---|---|---|
| pos-module-community | 41 ms | 23 ms | **21 ms** | 1558 → 1511 |
| arabbank | 177 ms | 38 ms | **30 ms** | 3236 → 3141 |
| Accala-MP | 903 ms | 81 ms | **33 ms** | 3289 → 2789 |
| htevent | 25 ms | 28 ms | 29 ms | 2906 → 2906 |

Anchoring beats the blacklist everywhere it matters and yields fewer candidates, so the
per-path work downstream shrinks too. htevent has no dependency trees, so all three are
within noise there — the anchored walk issues four globs instead of one.

The 187/262 ms figures in this task's description were single-process runs on a
differently loaded machine; the A/B above is the honest comparison.
