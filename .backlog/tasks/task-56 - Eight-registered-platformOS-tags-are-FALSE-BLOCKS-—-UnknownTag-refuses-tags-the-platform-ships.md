## Why

`UnknownTag` reports these eight, and it feeds `LiquidHTMLSyntaxError`, which **BLOCKS**. A false block is unappealable — the agent cannot override the write gate. Every one of them is a tag the platform ships.

| tag | our tool | runtime |
|---|---|---|
| `context_rc` | reports `Unknown tag` -> BLOCKS | exists |
| `execute_query` | BLOCKS | exists |
| `function_rc` | BLOCKS | exists |
| `query_graph` | BLOCKS | exists |
| `render_form` | BLOCKS | exists |
| `return_rc` | BLOCKS | renders |
| `sign_in_rc` | BLOCKS | exists |
| `try_rc` | BLOCKS | exists |

"exists" means `liquid_exec` errors for the tag's OWN reasons (missing argument, unclosed block) and never with `Unknown tag`, which is the discriminator — a bare `{% tag %}` fixture is expected to fail for tags that do exist, and that failure is not evidence of absence.

## The oracle, and it is better than a probe

`/home/ecgtheow/Work/desksnearme-release-candidate/config/initializers/liquid_view.rb` — the platform's own Liquid tag registry, the only non-test file in that repo calling `register_tag`. It holds 33 `Liquid::Environment.default.register_tag('name', Liquify::Tags::XTag)` lines; Liquid's built-ins (`assign`, `if`, `for`, `case`, …) come from the gem, so the registry is exactly platformOS's additions.

This is the SOURCE OF TRUTH for "does this tag exist", and it should be preferred over `liquid_exec` probing for that question. It was found while verifying TASK-44 — the same file independently confirms `layout` is NOT registered.

## Why both gates miss them

`detectUnknownTag` passes a tag if it is in `GRAMMAR_KNOWN_TAGS` (the parser's `NamedTags` + `TAGS_WITHOUT_MARKUP` + `BLOCKS` + `RAW_TAGS`) OR in the docset. These eight are in NEITHER: the grammar has no rule, and `packages/platformos-check-docs-updater/data/tags.json` (44 entries) does not list them.

Note `theme_render_rc` IS in the grammar while the other seven `_rc` variants are not, which suggests the omission is accidental rather than a decision.

## Approach — settle the `_rc` question FIRST

Five of the eight end in `_rc`, and `liquid_view.rb` marks `function_rc` with `# TODO: remove`. So there are two candidate populations and they deserve different treatment:

- If `_rc` tags are internal or deprecated, the fix is to stop BLOCKING on them without necessarily advertising them — an author should not be refused, but neither should completion suggest them.
- If they are supported, they belong in the vocabulary like any other tag.

Do not resolve that by reading the names. Check `Liquify::Tags::*` in that repo for what each does and whether the non-`_rc` form is an alias.

## Where the fix belongs

**Not** a hand-maintained list in `UnknownTag`. `data/tags.json` is regenerated by the docs-updater's `postbuild`, so an edit there is reverted by the next build — the docset is upstream-owned. Prefer widening the parser's vocabulary, or a generated companion list with a `scripts/verify-*.mjs` that reads the registry, following the established generated-file pattern.

Whatever the mechanism, the eight must stop blocking, and a genuinely unknown tag must STILL block — `{% no_such_tag_zzz %}` is the control.

## Falsifier

A registered tag in the table above that `liquid_exec` answers `Unknown tag` for.
